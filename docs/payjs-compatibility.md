# Payjs Native compatibility

The existing payjswescan and /pay/payjs/notify_url routes now use an application-owned Guzzle protocol client instead of the Xhat Laravel singleton. Merchant ID is still merchant_id and the communication key is still merchant_pem. Original orders, CNY cent amounts, QR rendering and plain success/fail notification acknowledgements remain. No schema or merchant setting conversion is required.

## Original protocol retained

PayjsClient sends an explicit form POST to the original fixed https://payjs.cn/api/native endpoint with mchid/body/total_fee/out_trade_no/notify_url. It takes current merchant credentials for every call, so another request's singleton cannot retain the previous account. The previous provider constructed a singleton from config once, while the controller merely changed config afterwards.

Signing retains the installed SDK's exact legacy byte rules: PHP truthy field filtering (including omitted numeric/string zero), sorted names, urldecode(http_build_query(fields) . '&key=' . key), and uppercase MD5. The URL decoding also applies to the key; this unusual existing behavior is deliberately preserved. Before uninstalling the real SDK, sign/checkSign produced AA527643E355C3174C9B3A5FBD47419E for the escaped-key/Unicode/zero fixture. Tests retain that captured vector alongside an independent fixed-field oracle. No SDK code is copied into vendor, and no new assumption that keys must have32 bytes is introduced.

Native responses require a valid signature under the current merchant key, return_code1, exact invoice and positive integer cent amount, a nonempty bounded payjs_order_id and a Native weixin QR. The legacy response need not echo mchid; if present it must match exactly. Wrong keys fail even without an account echo. JSON floats, nested/invalid scalar fields, malformed or oversized JSON, signed wrong invoices/amounts and non-Native QR targets fail. Requests enforce TLS verification, no redirects, connect3/total10-second bounds, a64KiB closed response stream and no automatic POST replay. Only an injected handler is inherited; foreign client defaults cannot override request/account/body/TLS fields.

## Explicit receipts and fulfillment

FormNotification extracts original string fields from the current bounded application/x-www-form-urlencoded body, avoiding global request state and Laravel TrimStrings/ConvertEmptyStringsToNull changes. It rejects malformed escaping, duplicate and encoded duplicate names, array keys and directive names. Alipay delegates its already-verified parser entry to the same utility; its route/cryptographic tests still pass.

Callbacks verify signatures with constant-time comparison and the current configured key, require a matching order reference and return_code1, use CNY when fee_type is absent, and enforce positive integer cents and a bounded transaction identifier. A signature-valid return_code0 or amount701.9 no longer reaches completedOrder. No provider exception or response payload is exposed to the browser.

Pay::find permits an already-paid disabled gateway's receipt recovery. The common receiptGuard rechecks order price, selected gateway, handler and three merchant fields inside the real order/stock/sales transaction and preserves enabled Stripe/PayPal binding exclusion. Provider I/O runs at transaction level zero. Same-transaction duplicates fulfill once; another transaction reference on a completed order fails. Expired paid orders enter the existing abnormal/manual state without consuming released stock. These modes do not add a durable unique creation object, webhook inbox, refund or background reconciliation.
