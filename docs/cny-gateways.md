# Alipay and WeChat gateway compatibility

The existing Alipay scan/web/wap and WeChat Native routes now have application-owned protocol boundaries. Merchant configuration, route names, CNY pricing and in-flight notifications remain compatible. The root still has Yansongda Pay2 with Laravel6/PHP7.4; the isolated Laravel12/PHP8.2 candidate actually runs Pay3.7.20. No root constraint, dependency lock, production credential or database schema was changed in the original Alipay/WeChat batch. The subsequent Payjs batch removes its unused wrapper and explicitly declares ext-dom, preserving all other locked versions.

## Why a constraint change is insufficient

Installed Pay3 Alipay StartPlugin unconditionally asks for app_public_cert_path and alipay_root_cert_path (or real certificate serials), while the current shop stores ordinary RSA keys. Its public callback supports RSA2 keys, but its default checkout pipeline is not compatible with the original no-certificate configuration. RawKeyAlipayStartPlugin uses the supported application plugin extension to omit only certificate serial generation. The provider's actual business, payload formatting, request signing, response signature verification and parsing plugins remain. It does not invent certificate serials or disable verification. Pay3 wap is mapped to its H5 shortcut.

Installed Pay3 WeChat scan uses the V3 JSON/RSA/certificate protocol. The existing app_id/mch_id/API-V2 key cannot supply a V3 signing certificate or verify V3 encrypted notifications. WechatV2Client therefore preserves the existing XML Native unifiedorder protocol independently of the installed SDK. This does not enable V3 or transform old payments; V3 is a separate future activation requiring explicit merchant certificate configuration and reconciliation of outstanding V2 orders.

## Configuration and request behavior

Alipay keeps merchant_id as App ID, merchant_key as the Alipay RSA public key, and merchant_pem as the application's RSA private key. Bare base64, PEM and the previous explicit local .pem/.crt paths are supported; OpenSSL validates the actual RSA key. Each call refreshes the SDK configuration instead of reusing another merchant's singleton. SDK2 logging uses NullLogger; SDK3 logger.enable=false. Controller errors and exceptions expose only a generic message/category.

The entry still accepts zfbf2f/alipayscan, aliweb and aliwap. Scan uses real provider response verification and requires the matching out_trade_no plus an HTTPS QR on qr.alipay.com. Web/wap return the real SDK's signed HTML with no-store headers; form construction has no provider network I/O. Prices are decimal strings; neither float conversion nor FX enters the checkout request.

WeChat keeps merchant_id as appid, merchant_key as mch_id and merchant_pem as the 32-byte API-V2 key. wescan still POSTs XML to https://api.mch.weixin.qq.com/pay/unifiedorder with NATIVE, a random nonce, MD5 signature, the original order reference and positive integer cents. A response requires transport/business SUCCESS, a valid MD5 or HMAC-SHA256 signature, matching appid/mch_id and a Native weixin QR. Optional echoed reference/amount must match the request.

Both network boundaries enforce fixed live HTTPS hosts, TLS verification, no redirects, connect3/total10-second bounds, a64KiB response limit and no automatic replay. External Guzzle defaults cannot replace the signed body, account headers or TLS options. Tests use a real Guzzle handler; they do not open provider connections.

## Receipt acceptance and fulfillment

Alipay explicitly decodes the current raw application/x-www-form-urlencoded POST body and passes its original string values to the SDK. This preserves whitespace/signature bytes despite Laravel TrimStrings/ConvertEmptyStringsToNull and avoids process globals. The bounded decoder rejects duplicate/array keys, malformed escapes and incompatible content types. Only matching App ID/order reference, CNY, TRADE_SUCCESS or TRADE_FINISHED, exact positive amount and nonempty transaction reference can complete an order. A signed pending/closed trade returns success without fulfillment. Signature or business mismatch returns fail.

WeChat reads the current request's raw XML; pre-verification parsing only selects the order's configured merchant. It bounds and rejects malformed XML, DOCTYPE/entities, namespaces, attributes, duplicate/nested fields and non-flat values, without external entity loading or persistent libxml configuration changes. It then verifies the exact signed fields with constant-time comparison and matches appid/mch_id. return_code/result_code must both be SUCCESS, trade_type NATIVE, fee_type CNY (the protocol default when absent), and total_fee a positive integer within theV2 range. No truncation of malformed decimal/exponent cents is accepted. The acknowledgement now uses the V2 XML return_code/return_msg structure with an XML Content-Type, replacing the old bare success/fail text.

Both controllers use PaymentGatewayLock.receiptGuard inside completedOrder's order transaction. It locks the actual gateway and rechecks order price, pay_id, route and all three merchant fields against the verified snapshot, then enforces any active Stripe/PayPal order binding. No provider request runs under those locks. Repeated same-transaction notifications consume one card and increment sales once; another transaction ID is rejected for a completed order. A closed gateway can still acknowledge a previously accepted payment. An expired paid order uses the existing abnormal/manual handling without consuming released stock or coupons.

The legacy modes do not introduce durable unique creation objects, background query/refund or signed inbox persistence for these two providers. With modern binding flags disabled, checkout selection retains the old cross-gateway behavior. Configuration rotation after payment must be reconciled before deleting the old account keys; the app does not retain historical private keys or guess another merchant.
